# botline — two-phase plan (v1, 2026-10-12)

Owner: Patrick Sabo (solo; a few hours a day; desk-only; SolarDecode is the main product and has no
customers yet). Author of this draft: Claude Code. Status: DRAFT for council review. Nothing built.

## 0. The one-paragraph thesis

People now run several vendors' agents at once (Claude Code, xAI's Grok Bot, Meta's Muse, OpenAI's Dots)
and the agents cannot talk to each other. No standard exists; the vendors only connect their own bots.
What every one of these agents *can* do is call a remote MCP server or a REST API over HTTPS, and most
have one native "doorbell" that wakes them (a webhook, an HTTP fire endpoint, a scheduled task, an email
address). botline is a tiny mailbox service that speaks MCP and REST, hands every agent its own key, and
rings each agent's native doorbell when mail arrives. Phase 1 ships it MIT-licensed and self-hostable on
Cloudflare's free tier and proves it on Patrick's own three agents. Phase 2 sells the hosted version to
people who own the agents but will never deploy a Worker.

## 2. Design rules that make Phase 2 cheap (apply from the first commit)

1. **One codebase, two deployments.** The self-host Worker and the hosted service are the same code.
   The only difference is configuration: `MODE=single` (one workspace, keys from env/CLI) vs
   `MODE=multi` (workspaces, signup, billing). No forks.
2. **Multi-tenant schema from day one.** Every table carries `workspace_id`. Self-host simply has one
   workspace. Retrofitting tenancy later is the expensive mistake to avoid.
3. **Adapters are plugins.** Doorbells live in `adapters/<kind>.ts` with one interface
   (`ring(agent, message) -> DeliveryResult`). Core never contains vendor logic. New vendor = new file.
4. **The envelope is the product's API.** Stable, boring, versioned (`v: 1`). Everything else can churn.
5. **Content is data, never authority.** Every body returned by the bus is wrapped as untrusted. The
   recipes tell each agent to treat it that way. This is a security feature and the marketing line.
6. **No secrets in logs, ever.** Keys are stored hashed; doorbell secrets encrypted with a master key
   from Workers Secrets; bodies are never logged.
7. **Billing and dashboard are separate Workers** that call the core's admin API. Core stays small.
8. **Measure from day one.** A hosted-interest waitlist link ships in the README of v0.1. That number
   is the Phase 2 gate.

## 3. Phase 1 — open source, self-hosted, proven on us

### 3A. Spike (one working day; go/no-go before anything else)

Build the smallest thing that answers the two unknowns no documentation answers.

Build (Claude Code, ~2 h): a Worker with `POST /v1/send`, `GET /v1/inbox/:agent`, `POST /v1/ack`, and
`/mcp` (streamable HTTP; tools `inbox_list`, `message_send`, `message_ack`); per-agent bearer keys from
env; D1 table `messages`. Deployed to a throwaway `*.workers.dev` URL.

Connect (Patrick, ~1 h, each step 5–15 min):
- Claude: add the URL as a claude.ai custom connector with a fixed `Authorization` header; create one
  cloud routine with an API trigger whose prompt says "call inbox_list, act on the routine-fire-payload,
  reply with message_send"; copy its `/fire` URL + token into the Worker as Claude's doorbell.
- Grok Bot: add the URL as a custom MCP server with the Authorization header (if the field exists) —
  else the fallback is REST via `curl` from the box, with the key stored as a Secret; create one routine
  with a webhook trigger whose prompt says the same; copy webhook URL + key into the Worker as its
  doorbell. Local execution stays at Ask.
- Muse: in chat, give it the `/mcp` URL and the key, ask it to build the bridge and save it as a skill;
  then create a scheduled task "every 15 minutes, call inbox_list; reply with message_send"; click
  "Always allow" on both tools when prompted. If the account has "Create an email", claim an address and
  record whether a mail to it wakes Muse (second doorbell).

Measure: one three-way round trip (Claude -> Grok Bot -> Muse -> Claude), timing each hop, counting
human clicks after first-time approvals, and recording exactly which auth each vendor accepted.

Go/no-go (all three must hold, else stop and rethink the Muse story before writing more code):
- G1 Muse calls the bus from a scheduled task with zero prompts after one "Always allow".
- G2 Grok Bot reads and posts via MCP-with-header or REST, and its webhook doorbell starts a routine
  that reads and replies without a human click.
- G3 Claude's `/fire` doorbell starts a routine that reads and replies; claude.ai connector works.
Target: full loop under 10 minutes; Muse's hop is bounded by its polling interval.

### 3B. v0.1 (four to six working sessions)

Stack: Cloudflare Worker (TypeScript), D1, Durable Object per inbox for ordering and doorbell retry
queue, Workers Secrets. Framework and MCP transport library to be chosen at build time against current
docs (Context7 was down while drafting; candidates: Cloudflare `agents` McpAgent vs a stateless
streamable-HTTP handler). Node + SQLite self-host variant is v0.2, not v0.1.

Deliverables:
1. **Core API** — REST and MCP, identical semantics:
   `me`, `agents_list`, `message_send`, `inbox_list(unread|all, since)`, `message_ack`, `thread_get`.
   Per-agent bearer key `bl_<8>_<32>`; hashed at rest; `me` returns agent identity and workspace.
2. **Envelope v1** — `id, v, workspace_id, thread_id, from, to[], subject, body (markdown, <= 32 KB),
   needs (reply|ack|none), attachments[] (URLs only), created_at, expires_at, delivered_at[],
   read_at[], acked_at[], meta{}`. Bodies returned inside an explicit untrusted-content wrapper.
3. **Doorbell adapters** — `grokbot_webhook`, `claude_fire`, `generic_webhook`, `email` (via Resend
   API; Patrick already holds a Resend account), `none` (poll). Retries with backoff; dead-letter after
   N; receipts recorded (`delivered_at` on 2xx, `read_at` when `inbox_list` returns it, `acked_at`).
4. **Conformance script** — `botline-check` runs the three-way loop against any deployment and prints
   the hop table. The output of this script on Patrick's agents is the launch asset.
5. **Recipes** — one page per vendor: how to connect, which auth worked, which doorbell, what needs
   approval, known limits (Grok Bot email send = approval every time; Muse = no push; Claude cloud
   routine min 1 h schedule / 30 fires per hour). This is the content nobody else has.
6. **Self-host path** — `wrangler deploy` plus a "Deploy to Cloudflare" button; `botline agent add`
   CLI prints a key; README under 200 lines; LICENSE MIT; prior art credited by name on day one.
7. **Waitlist** — one line in the README: "Don't want to host it? Join the hosted waitlist" ->
   a form that writes to a D1 table on Patrick's own deployment (no third-party form tool).

Explicitly out of v0.1: ChatGPT/Dots adapter (v0.2, invite a contributor), attachments as blobs,
web UI, OAuth for the bus itself, Node/SQLite variant, Slack/Discord bridges, encryption of bodies
beyond D1 at-rest, teams/roles.

### 3C. Launch (one session, the day v0.1's conformance run passes)

- README leads with the hop table and a 30-second recording of the three-way loop.
- Posts: Show HN; the Cursor forum thread "Grok Bot: can I send it a message from outside?"; r/ClaudeAI;
  Muse communities; X. One message everywhere: "the first bus proven across Claude, Grok Bot and
  Muse; MIT; self-host free; hosted waitlist if you'd rather not."
- Instrumentation: GitHub traffic (clones/visitors), stars, waitlist count, issues by vendor.

### Gate to Phase 2 (decided by signal, time-boxed)

Start Phase 2 the day **either** holds: 25 hosted-waitlist signups, or 300 stars. Hard stop check at
day 21 after launch: under 10 signups and under 100 stars -> botline stays an OSS tool for our own use;
no hosted product; time goes back to SolarDecode. Between those bands: Patrick decides.

## 4. Phase 2 — the hosted service (five to seven sessions after the gate)

Product: **botline cloud**. One plan, one price, free tier to seed.
- Free: 2 agents, 100 messages/month, 7-day retention.
- $9/month flat: 10 agents, 10,000 messages/month, 30-day retention, all doorbells, email receipts.
  (CrossWire anchors $9 Starter / $29 Pro with fewer features; we undercut Pro and out-feature Starter.
  No enterprise tier in year one.)

Build (same codebase, `MODE=multi`):
1. Workspaces + signup by magic link (Resend). Each workspace = isolated keys, agents, doorbells.
2. Stripe Checkout + webhook -> `workspace.plan`; Stripe Customer Portal for cancel/receipts
   (Patrick already runs Stripe live for SolarDecode).
3. Minimal dashboard (static page + core admin API): agents, keys (show once), doorbells with "ring
   test", message log with receipts, usage meter, delete workspace.
4. Hosted deployment at `api.botline.dev`; status page; retention job; export + delete endpoints.
5. Canaries: Patrick's own Claude/Grok Bot/Muse run the conformance loop daily; a failed hop pages via
   the existing `notify.sh` (Pushover). This is how we learn a vendor broke an adapter before customers
   do — and it is the service people pay for.
6. Terms + privacy: message bodies are customer data; never used for training; 30-day retention on
   paid, 7 on free; deleted on workspace deletion; no reading of bodies for support without consent.

Go-to-market: convert the waitlist first (they asked); then the recipe pages as SEO ("connect Muse to
Claude", "Grok Bot webhook from Claude Code"); then the vendors' own communities. No ads.

Unit economics: Cloudflare free/paid tier covers thousands of workspaces for under $25/month; Resend
free tier for mail; Stripe fees ~3%. Break-even is effectively the domain name. The constraint is
Patrick's hours, not infrastructure.

## 5. Risks and the answer to each

| Risk | Likelihood | Answer |
|---|---|---|
| A vendor ships cross-vendor messaging and the gap closes | High over 6–18 months | Speed; open standard posture (envelope published, MIT); the adapters + canaries remain useful even if one vendor adds native support; stop rule at day 21 limits sunk cost |
| Muse connector auth is disputed (API key vs OAuth) and no push | Certain today | Spike G1 settles it in one hour; Muse polling interval is documented as a product limit, not hidden |
| Grok Bot custom MCP needs OAuth (header field absent) | Medium | REST fallback from its box with a Secret; spike G2 |
| Prompt injection between agents | Certain in the wild | Untrusted wrapper on every body; per-agent allowlists in v0.2; recipes say "data, not instructions"; this is the headline safety feature |
| Grok Bot "Always allow" local execution | N/A | Not needed: botline never touches local files; local execution stays at Ask |
| ToS | Low | Every entry point is an official vendor surface (connectors, routines, scheduled tasks). We never drive a vendor's UI or WebSocket (unlike Muse-Chat-MCP) |
| Name / trademark | Low | botline: clear on npm, PyPI, GitHub; `.dev` unregistered at check time. Not "hatchline" (Hatch is Muse's internal name) |
| Support burden on a solo founder | Medium | Canaries + recipes; hosted tier only after demand; free tier capped; no SLA language |
| Focus drain from SolarDecode | High | Hard time boxes: spike 1 day, v0.1 <= 6 sessions, launch 1 session, Phase 2 only past the gate |

## 8. Questions for the council

1. Is the multi-tenant-from-day-one rule worth its cost in Phase 1, or is `workspace_id` on every
   table enough and the rest (signup, plans) should wait? Where exactly is the line?
2. Doorbell semantics: ring on every message, or coalesce per agent (ring at most once per N seconds
   while unread mail exists)? Grok Bot has 30 fires/h/routine on Claude's side and unknown limits of its
   own; every ring costs the user money on their agent plan.
3. Receipts: is `read_at = inbox_list returned it` an honest "read"? Alternatives?
4. Is the untrusted-content wrapper enough, or should v0.1 already include per-agent allowlists
   ("muse may message claude; nothing may message grokbot except claude")?
5. The gate numbers (25 signups / 300 stars, stop under 10/100 at day 21): too loose, too tight?
6. Pricing: $9 flat with a free tier, versus free-only until a second signal, versus $5?
7. Anything in the spike's go/no-go that would let us ship something that does not actually work?
8. What is missing that a solo operator will regret in month three?
